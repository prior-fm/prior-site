MCP and APIs

Why a second protocol, when the first one still works

An API is two programs talking, and it has worked for twenty years. The trouble starts at ten services and two apps, where the same authentication, request code, error handling and retries get written twenty times over and then maintained in parallel. MCP does not replace any of it — it puts one standard client in each app, one small server beside each service, and turns a multiplication into a sum.

The part people get wrong
The model never makes the call

The model emits text — the name of a tool and some arguments. Your code reads that text and decides whether to run it. That is where every guardrail you want has to live, because it is the only part of the system with a network stack.

The pack
Run the argument

Two MCP servers, two apps, and a script that counts the integrations for you.

TypeScript, no API keys, no accounts, no network — it runs offline. The second app is nineteen lines and not one of them is an integration, which is the whole claim made checkable. npm run count -- 8 30 prints what your own numbers cost each way, including the cases where MCP is the wrong choice.
