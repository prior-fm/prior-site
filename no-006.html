A counter says ([)] is fine. The stack knows it is not

Walk the string once. Every opening bracket goes onto a stack; every closing bracket has to match the one on top, or the string is invalid there and then. At the end it is valid only if the stack is empty. Eleven lines, one pass, and the whole thing turns on a single idea: the stack remembers which brackets are still open, in the order they were opened.

The thing worth noticing
A counter
knows how many.
A stack knows
which ones.

Almost everyone writes the counter first, and for one bracket type it is genuinely correct — add one for (, subtract one for ), never go below zero, finish at zero. The moment there are three types it stops working, because a number has no memory of what it counted. ([)] has two openers and two closers and a counter is perfectly happy with it.

The pack measures how often that matters, exhaustively rather than by sampling — every string over ()[]{} of a given length. At length 8 there are 90,720 strings the counter and the stack disagree about, out of 1,679,616. That is 5.4%, and it falls with length only because long random strings are overwhelmingly invalid in ways both methods catch.

The number that actually matters is a different one. Of all those disagreements, the count of times the counter wrongly rejects a valid string is zero. Every single one is a false accept — the counter waving through input the stack catches. That is the direction of failure that reaches production, because nothing downstream ever complains about input that was let in.

And the part the film has no room for
The same stack,
on a model’s
streaming output

A model streams JSON a token at a time and you want to act the moment a complete value has arrived. The usual approach is json.loads() on every prefix inside a try/except. It works, and it re-parses the entire prefix every time — O(n²) to answer a question the stack answers in one pass. On an 18,000-character document one run here measured 1,612.6 ms against 6.1 ms for the same answer — 265×. Repeat runs on the same laptop landed between 249× and 291×, so treat the ratio as an order of magnitude and not a benchmark. Your numbers will differ; the exponent will not.

A stack also gives you something a boolean cannot: the closing suffix is the stack read backwards. Not just whether the stream is unbalanced, but exactly what would balance it — so you can show a user the largest piece of the answer that is real JSON, mid-stream, without ever handing them something that fails to parse.

One rule the film does not need and yours does: a bracket inside a string is not a bracket. {"note": "a } inside a string"} is valid JSON, and a bare bracket stack rejects it at character 8. A JSON scanner needs a string flag as well as a stack, and a backslash flag as well as that. It is the single most common bug in hand-rolled streaming JSON handling, and it only shows up on the inputs that contain user text — which is most of them.

The pack
Run it
and check
the claim

The counter, the stack, and the streaming JSON scanner built on it. Python, no dependencies.

python run.py and nothing else. Three acts, about two seconds: every string of length 2, 4, 6 and 8 checked both ways with the disagreements counted; the scan printed step by step for a valid string and an invalid one; and the same stack timed against json.loads-per-prefix on a streaming document. There is no randomness anywhere in it — acts one and two are exhaustive and fixed, and the only varying number is a wall-clock timing.

Also in there: truncate_to_valid, which refuses to close a partial stream immediately after {, [, , or :. Closing there would parse — and it would hand back an element the model never sent. Truncating is honest; inventing an empty object is not, and it is worse than useless because it parses.
